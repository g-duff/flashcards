# Async Rust Through the Server

This guide explains the async Rust ideas used in [`server/`](../server/).
The examples are deliberately tied to this codebase rather than being a
general async tutorial.

## The one-sentence mental model

An async function describes work that can pause; a runtime such as Tokio
keeps polling that work and runs other work while it is paused.

```text
async Rust code
      |
      | creates a Future (a suspended computation)
      v
Tokio runtime
      |
      | polls ready work, waits for I/O, wakes paused work
      v
OS threads + network/database activity
```

Async is about *when a task gives up the thread*, not automatically about
creating a new thread. A server can handle many waiting requests without
assigning one blocked thread to each request.

## Who provides which piece?

| Concept in this guide | Provided by |
| --- | --- |
| `async fn` and `.await` syntax | Rust language |
| `Future`, `Poll`, `Context`, `Waker` | Rust standard library (`std::future`, `std::task`) |
| `Pin` | Rust standard library (`std::pin`) |
| `Result`, `Option`, ownership, borrowing, `Arc` | Rust language and standard library |
| An executor/runtime that drives futures | Tokio |
| `#[tokio::main]` and `#[tokio::test]` | Tokio procedural macros |
| `tokio::net::TcpListener` | Tokio |
| `tokio::spawn` | Tokio |
| HTTP routing and handler extraction | Axum |
| Async SQLite queries and connection pooling | SQLx, configured with Tokio support |

Rust defines the async *interfaces and syntax*, but the standard library does
not provide a general-purpose async runtime. Tokio is the engine used by this
server.

## 1. `async fn` returns a future

This handler does not execute all of its body when it is called:

```rust
pub async fn list_learners(
    State(state): State<AppState>,
) -> Result<SuccessEnvelope<Vec<Learner>>, ErrorResponse> {
    let learners = repository::list(state.db()).await.map_err(internal_error)?;
    Ok(envelope::success(learners, Utc::now()))
}
```

An `async fn` is roughly like a function whose return value is an unnamed
future:

```text
call list_learners(...)
          |
          v
Future<Result<SuccessEnvelope<...>, ErrorResponse>>
          |
          | Tokio/Axum polls it
          v
body runs until the next incomplete operation
```

The future is a state machine generated by the compiler. It remembers local
variables and the point at which it paused, so it can continue later.

`async fn` and `.await` are Rust language features. The generated future uses
the standard library's `Future` trait, but Tokio is responsible for actually
driving it in this application.

## 2. `.await` is a cooperative pause

In the repository, SQLx starts an asynchronous database operation:

```rust
let rows = sqlx::query_as::<_, LearnerRow>(SQL)
    .fetch_all(pool)
    .await?;
```

The important distinction is:

```text
.await on an operation that is not ready
    |
    +--> current task yields its thread
    |
    +--> Tokio runs another ready task
    |
    +--> database/socket becomes ready and wakes this task
    |
    +--> Tokio polls this task again
```

This is different from a blocking call:

```text
blocking database/read call
    |
    +--> the OS thread waits and cannot run another task
```

An `.await` does not mean "start a background task." It means "continue this
function when this future completes." Sequential awaits remain sequential:

```text
connect().await
      |
      v
migrations.load().await
      |
      v
migrations.run().await
```

That is the flow in
[`db::connect_and_migrate`](../server/src/db.rs). Each operation must finish
before the next line can use its result.

## 3. Tokio starts the runtime

The program entry point is:

```rust
#[tokio::main]
async fn main() {
    // ...
}
```

The `async fn main` part is Rust. The `#[tokio::main]` attribute is Tokio. The
attribute generates ordinary startup code that creates a Tokio runtime and
runs `main` on it.

```text
process starts
      |
      v
#[tokio::main] builds Tokio runtime
      |
      v
async main is executed
      |
      +--> connect and migrate database
      |
      +--> bind TCP listener
      |
      +--> await the HTTP server
```

The final `.await` in `main` keeps the process alive while Axum serves
requests:

```rust
axum::serve(listener, app)
    .await
    .unwrap_or_else(|error| panic!("server error: {error}"));
```

Tokio's runtime normally uses a pool of worker threads. Futures are cheap
units of suspended work; they are not themselves OS threads.

## 4. The server's request flow

`main` binds a Tokio TCP listener and gives it to Axum:

```rust
let listener = tokio::net::TcpListener::bind(addr).await?;
axum::serve(listener, app).await?;
```

```text
TCP connection arrives
          |
          v
Tokio TcpListener reports readiness
          |
          v
Axum accepts and parses the HTTP request
          |
          v
router selects a handler
          |
          v
handler runs until it awaits SQLx
          |
          +--> task pauses while SQLite work is pending
          |
          v
handler resumes, builds response
          |
          v
Axum writes HTTP response
```

`tokio::net::TcpListener` is Tokio. The router and handlers are Axum. The
`async fn`, `.await`, and future state machines are Rust.

## 5. Why handlers can be ordinary-looking

Axum invokes async handlers such as `get_health` for separate requests. The
handler looks linear:

```rust
sqlx::query("SELECT 1")
    .execute(state.db())
    .await
    .map_err(|source| /* convert error */)?;

Ok(envelope::success(/* ... */))
```

The linear syntax is useful: it expresses the logical order without manually
writing callbacks. While the database future is pending, Tokio can poll other
request futures.

The `?` operator is not Tokio. It is Rust syntax for propagating a `Result`
error:

```text
Ok(value)       -> continue
Err(error)      -> return early from this async function
```

The handler's return type is also ordinary Rust:

```rust
Result<SuccessEnvelope<HealthData>, ErrorResponse>
```

The async part is the future wrapped around that eventual `Result`.

## 6. Shared state, ownership, and `Arc`

Every handler receives an `AppState` clone. `AppState` stores its contents in
the standard-library `Arc`:

```rust
pub struct AppState(Arc<AppStateInner>);
```

```text
Router owns AppState
       |
       +--> request 1 clones AppState --+
       |                                |
       +--> request 2 clones AppState --+--> same AppStateInner
       |                                |       |
       +--> request 3 clones AppState --+       +--> SqlitePool
                                               +--> Config
```

Cloning an `Arc` clones a small reference-counted pointer, not the database
pool and configuration. This makes it possible for concurrent handlers to
share read-only application state safely.

`Arc` is standard library (`std::sync::Arc`). `SqlitePool` is SQLx; it is
designed to be shared and to manage multiple database connections.

The server does not use `std::sync::Mutex` or a Tokio mutex in the code shown.
If shared mutable state is added later, choosing between a synchronous mutex,
`tokio::sync::Mutex`, channels, or another design depends on whether the
critical section performs async work. Holding a blocking mutex across `.await`
is generally a warning sign.

## 7. Tasks: the test server example

The integration-test helper starts a server in the background:

```rust
tokio::spawn(async move {
    axum::serve(listener, app)
        .await
        .expect("test server failed");
});
```

```text
test task
   |
   +--> tokio::spawn(server future)
   |
   +--> return base URL immediately
   |
   +--> send test HTTP requests

server task
   |
   +--> await Axum server forever
```

`tokio::spawn` creates a Tokio task and schedules it on the runtime. It does
not necessarily create a new OS thread. The `async move` block takes ownership
of `listener` and `app`, allowing the spawned task to outlive the current
function call.

The returned `JoinHandle` is ignored in this helper because the test only
needs the server to run while the test executes. In production code, a
`JoinHandle` can be awaited to observe task completion or failure.

## 8. What happens at an `.await`

At a high level, a future follows the standard-library `Future` protocol:

```text
poll future
   |
   +--> Poll::Ready(value)
   |       future is complete
   |
   +--> Poll::Pending
           future cannot continue yet
           register a Waker
           return control to the runtime
```

`Future`, `Poll`, `Context`, and `Waker` are standard-library concepts. Tokio
uses them to schedule work, but application code normally only sees `.await`.

The future must eventually be woken when its input becomes ready. Tokio's I/O
driver and SQLx integration arrange that wake-up for network and database
operations.

## 9. Async does not make CPU work cooperative automatically

Tokio can only switch tasks when the current future yields, commonly at an
`.await`. A long CPU loop with no awaits can prevent other tasks from making
progress on that worker thread:

```text
async handler
   |
   +--> huge CPU loop with no .await
           |
           +--> other tasks wait on the same worker
```

For expensive CPU-bound work, use an appropriate Tokio blocking or dedicated
thread strategy rather than putting a large synchronous computation directly
in a request future. This server currently performs short validation and
response transformations, while database and socket waits are async.

## 10. How to read this server

When you encounter async code, ask these questions in order:

1. **What is the future?** Find the `async fn`, async block, or async library
   method being called.
2. **Where can it pause?** Look for `.await`. Everything before the next
   incomplete await runs on the current task.
3. **Who drives it?** In this project, the Tokio runtime starts in
   `#[tokio::main]`; tests use `#[tokio::test]`.
4. **What wakes it?** Usually Tokio I/O or a library such as SQLx.
5. **What is shared?** Follow `AppState` and `Arc`; check whether values are
   borrowed, moved into an `async move` block, or cloned.
6. **What is the error path?** Read the `Result` type, `?`, and `map_err`
   transformations. They are Rust error handling, not async-specific.

The main execution path is:

```text
#[tokio::main]
      |
      v
Tokio runtime
      |
      v
axum::serve(listener, app)
      |
      v
async handler
      |
      v
SQLx future --await--> Tokio schedules other work
      |
      v
handler resumes and returns Result
      |
      v
HTTP response
```
